# Research and component choices (M0)

Goal: send *selected* HTTP(S) requests from PHP through a WireGuard provider
(e.g. Surfshark manual configs) without root, TUN devices, route changes,
proxy daemons or separately installed packages, with DNS through the tunnel
and fail-closed behaviour. Survey date: October 2026.

## Existing approaches

| Approach | Why it does not fit on its own |
|---|---|
| Kernel WireGuard / `wg-quick` | Needs root/`CAP_NET_ADMIN`, changes routes, affects the whole host. |
| [wireproxy](https://github.com/windtf/wireproxy) (Go, wireguard-go + gVisor netstack, SOCKS5/HTTP proxy) | Userspace and works well, but it is a separate daemon to install and supervise. The architectural model for this project. |
| [onetun](https://github.com/aramperes/onetun) (Rust, boringtun + smoltcp, MIT) | Port forwarder daemon; confirms boringtun + smoltcp is a workable userspace stack. |
| mitmproxy WireGuard mode (Rust, boringtun + smoltcp + tokio) | Server side, but same building blocks. |
| PHP extensions / libraries | None found that embed a WireGuard client. PHP curl can only use an external SOCKS/HTTP proxy. |

## Language for the core

| | Rust | Go (c-shared) |
|---|---|---|
| Runtime in a `dlopen`ed module | none; lazily created per process | Go runtime starts at load time |
| PHP-FPM / Apache prefork (`MINIT` in the master, then `fork()`) | safe: nothing exists before first use; PID check discards state inherited over `fork()` | runtime threads do not survive `fork()`; known breakage in forked children |
| Signals | no handlers installed | Go installs its own handlers (conflicts with PHP's) |
| Several modules in one process | fine (symbols hidden) | only one Go runtime per process |
| Userspace stack | boringtun + smoltcp (+ rustls, hyper) | wireguard-go + gVisor netstack (most mature) |

Decision: **Rust core + thin C Zend shim**. The C side uses the official Zend
API and `phpize`, so one source builds for PHP 8.0–8.5 (`vpn_arginfo.h` is
generated by PHP 8.5's `gen_stub.php` with legacy arginfo down to 8.0).
ext-php-rs was not used to avoid coupling PHP-version support to a binding crate.

## WireGuard implementation

| Crate | License | Status (Oct 2026) | Notes |
|---|---|---|---|
| **boringtun 0.7.1** (Cloudflare) | BSD-3-Clause | 0.7.0 Jan 2026, 0.7.1 May 2026 (maintained again) | `noise::Tunn` works on byte buffers (encapsulate / decapsulate / timers), no TUN device needed. Pure-Rust crypto (RustCrypto: chacha20poly1305, x25519-dalek, blake2). **Chosen.** |
| gotatun 0.10 (Mullvad fork of boringtun) | MPL-2.0 | very active (0.10.2 Oct 2026) | Also exposes `noise::Tunn`, but with its own packet types; default crypto backend aws-lc-rs (C + cmake build). Good fallback; file-level copyleft is compatible with linking but adds obligations. |
| NepTUN (NordSecurity fork) | BSD-3-Clause | not on crates.io | Not evaluated further. |
| wireguard-go | MIT | maintained | Go only (see above). |

boringtun sits behind the small `tunnel.rs` wrapper, so switching to gotatun is
contained to one file.

## Other components

| Component | Crate | License | Why |
|---|---|---|---|
| TCP/IP + DNS client | smoltcp 0.14 | 0BSD | Embedded stack with a DNS socket and async wakers; `Medium::Ip` maps directly onto WireGuard's layer-3 tunnel. |
| HTTP/1.1 | hyper 1.x (client conn API) | MIT | Correct framing (chunked, content-length, pipelining rules) over any `AsyncRead + AsyncWrite`. |
| Runtime | tokio (current-thread) | MIT | No worker threads; `block_on` inside the PHP call. |
| TLS | rustls 0.23 (ring provider) + webpki-roots | Apache-2.0/ISC/MIT, CDLA-Permissive-2.0 (roots) | No OpenSSL symbols to clash with PHP's own; bundled Mozilla roots make the module self-contained. |
| Decompression | flate2 (rust backend) | MIT/Apache-2.0 | gzip/deflate with size caps. |

## Findings that shaped the design

* **One live session per key.** A WireGuard server keeps one session and one
  endpoint per peer public key. Two processes using the same key replace each
  other's session. Hence the cross-process `flock()` per key, the "who
  handshook last" record in the lock file, and `VPN::pool()` for parallelism.
* **Handshake flood protection.** Linux WireGuard drops an initiation that
  arrives within 20 ms of the previous one for the same peer. Processes taking
  over a key wait 30 ms after the last recorded handshake.
* **tokio `try_send` readiness.** tokio does not attempt a send on a freshly
  registered socket until the reactor has reported writability; the first
  handshake was silently dropped. Datagrams are sent through a plain `std`
  clone of the socket.
* **Endpoint host names** (e.g. `de-fra.prod.surfshark.com`) can only be
  resolved by the host resolver, before the tunnel exists. This reveals the VPN
  server name, never a destination. Use an IP endpoint to avoid it.
